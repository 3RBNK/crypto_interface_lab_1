# AES / Windows CNG

Режим `CFB` в этой программе означает **CFB-128 без padding**.
Он несовместим с CFB-8, который Windows CNG выбирает по умолчанию.
Размер feedback явно задаётся через `BCRYPT_MESSAGE_BLOCK_LENGTH = 16`.

## Причина проблемы с enc_cfb.bin

- Файл содержит 1864 байта: 1856 байт полных блоков и 8 байт остатка.
- Ключ: `secret_key.bin`, IV: `enc_cfb_iv.bin`.
- Правильная расшифровка побайтно совпадает с `result2.txt`.
- `result.txt` совпадает с результатом применения CFB-8 к этому CFB-128 файлу.

В CNG CFB-128 без padding не принимает неполный блок. Включение
`BCRYPT_BLOCK_PADDING` при расшифровке не исправляет файл, который был
зашифрован без padding. Переключение на CFB-8 также меняет результат.

`crypt_cfb128` в `utils.c` временно дополняет входной буфер нулями до
кратного 16 размера. Весь буфер обрабатывается одним `BCryptEncrypt` или
`BCryptDecrypt` в режиме CFB-128, с флагами `0`. Затем копируются только
первые N байт результата, где N — исходный размер входа. Например, для
`enc_cfb.bin` в памяти обрабатываются 1872 байта, а сохраняются 1864 байта.

Это работает для CFB: добавленные в конец байты не влияют на расшифровку
предыдущих байтов. При шифровании сохраняются также только исходные N байт.
Нули добавляются **только в памяти**, исходные файлы не изменяются.
Настоящие нулевые байты в конце данных сохраняются: обрезание определяется
длиной, а не значениями байтов. Пустой вход даёт пустой выход.

Ручного XOR, переключения на ECB и сторонних криптографических библиотек
нет. Дополнение не является PKCS#7; `BCRYPT_BLOCK_PADDING` для CFB не
используется. CBC и ECB используют прежний `BCRYPT_BLOCK_PADDING`.

Документация Microsoft:
[свойства CNG](https://learn.microsoft.com/en-us/windows/win32/seccng/cng-property-identifiers),
[BCryptDecrypt](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptdecrypt).

## Сборка и запуск на Windows

В Developer Command Prompt для Visual Studio, из корня проекта:

```bat
build_windows.cmd
```

Нужны MSVC с поддержкой `/std:c11` и Windows SDK (компоненты разработки
на C++ в Visual Studio), целевая ОС — Windows 10/11. Скрипт собирает приложение и
тесты, запускает проверки, расшифровывает `enc_cfb.bin` и побайтно сравнивает
результат с `result2.txt`. При любой ошибке возвращает ненулевой exit code.
Все результаты сборки и расшифровки помещаются в `build/`.
В `.gitattributes` для `result2.txt` зафиксированы окончания строк LF:
Git на Windows не должен менять байты эталонного текста на CRLF.

Повторный запуск расшифровки после сборки:

```bat
build\crypto_fixed.exe decrypt CFB secret_key.bin enc_cfb.bin enc_cfb_iv.bin build\decrypted_cfb.txt
fc /b build\decrypted_cfb.txt result2.txt
```

Можно также пересобрать проект Visual Studio. `bcrypt.lib` подключена через
директиву в `crypto.h`. Старые `crypto.exe` и `main.exe` не обновляются при
изменении исходников — нужно запускать вновь собранный файл.

Для ECB аргумент IV всё равно требуется интерфейсом командной строки;
можно указать `-`, файл IV в этом режиме не используется.
При ошибках программа возвращает ненулевой exit code и печатает NTSTATUS
в шестнадцатеричном виде.

## Проверки

`build_windows.cmd` запускает `tests/cfb128_test.c`: известный вектор
NIST SP 800-38A F.3.13, все его префиксы длиной 0–64 байта и файл
`enc_cfb.bin`, в обоих направлениях. Дополнительно проверяются сохранение
концевых нулей, неизменность IV, граница выходного буфера и защита от
переполнения размера при округлении. Входные файлы не изменяются.

На macOS проверены эти же C-исходники с временной тестовой заменой вызовов
CNG на OpenSSL: вектор и его префиксы, исходный файл, 99 циклов шифрования
и расшифрования для CFB/CBC/ECB и ключей 128/192/256 бит. Шифротексты также
сравнены с OpenSSL независимо от обратной расшифровки. Сборка выполнялась
с AddressSanitizer и UndefinedBehaviorSanitizer. Эти проверки подтверждают
логику кода, но не заменяют приведённый выше тест с настоящим CNG на Windows.
